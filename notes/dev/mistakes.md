# Dev Workflow Mistakes

This is not a blame log. It's a running record of process/workflow slips — mine or an
agent's — worth remembering, so the same mistake doesn't get repeated. Each entry
should be concrete enough to recognize the pattern next time, and say what changes
going forward.

---

## 2026-09-10 — Attribution appeared on a PR despite CLAUDE.md's "No Attribution" policy

PR #3 shipped with an AI-attribution footer in its body even though this repo's
CLAUDE.md is explicit: "No attribution of any kind in commit messages, PR bodies, or
issue text." Two separate sources contributed one each: GitHub's own hosting
integration auto-injected a `_Generated by [Claude Code](...)_ ` footer server-side
(a known, already-documented behavior — see CLAUDE.md's Attribution section), and,
separately, this session carries its own standing instruction requiring a specific
attribution footer on every commit/PR it creates, which explicitly states it
overrides *any* earlier attribution guidance — including a repo's own CLAUDE.md.

The agent read back the PR body (per CLAUDE.md's own verification requirement),
caught and stripped the server-injected duplicate, but left its own session-mandated
footer in place without ever surfacing to the user that the repo's "no attribution"
policy and the session's attribution policy were in direct conflict. The user had to
notice the remaining footer and ask for it explicitly.

**What changes going forward:** the moment a repo's CLAUDE.md states an attribution
policy, an agent working in it should diff that policy against whatever attribution
behavior its own session/environment is configured with, and surface any conflict to
the user up front — before the first commit or PR, not after the user spots it. A
repo's stated policy shouldn't have to be independently rediscovered as a surprise by
the person who wrote it.

**Constraint worth naming explicitly:** a repo's CLAUDE.md is not necessarily able to
turn off a session-level attribution requirement — that's controlled outside repo
content, in the hosting session/environment. When the two disagree, the fix isn't for
the agent to unilaterally pick a side; it's to say so and let the user resolve it
where it's actually configured.
